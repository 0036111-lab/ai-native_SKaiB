# Context Engineering

Собирай для каждого шага агента минимальный высокосигнальный контекст, достаточный для правильного действия. Не считай RAG всей системой: retrieval — только один из поставщиков контекста.

## Сначала установи границу фактов

- Для существующей системы сначала изучи доступные конфигурации, код, сервисы, логи и документацию read-only.
- Разделяй `подтверждено`, `настроено, но не проверено`, `неизвестно` и `предлагается`. Не изображай целевую архитектуру как текущую.
- Не называй интеграцию рабочей без наблюдаемой проверки маршрута от запроса до результата.
- Не записывай данные в память, индекс или внешнюю систему без разрешения, которое следует из задачи.

## Выбери режим

1. **Аудит:** восстанови фактический путь контекста, найди потери, дубли, переполнение, смешение прав и неподтверждённые write-back.
2. **Проектирование:** задай context contract, источники, сборку, бюджеты, память, наблюдаемость и безопасную запись.
3. **Диагностика:** воспроизведи сбой и установи, на каком этапе контекст не найден, не допущен, неверно ранжирован, обрезан, устарел или проигнорирован моделью.

## Собери карту контекста

Учитывай каждый класс отдельно:

- **Control:** system/developer instructions, policies, role, skills, output contract.
- **Task:** цель, проект, пользователь, стадия работы, ограничения, критерий завершения.
- **Working state:** план, незавершённые действия, промежуточные результаты, последние релевантные сообщения.
- **Knowledge:** RAG, файлы, базы, документы, live API; у каждого фрагмента — источник, время и область доступа.
- **Tools:** только релевантные определения инструментов; результаты инструментов очищай, агрегируй или сжимай после использования.
- **Memory:** профиль пользователя, проектные решения, эпизоды, уроки процесса и артефакты — не смешивай их в одну безымянную память.

Для подробной таксономии и архитектурных решений прочитай [references/patterns.md](references/patterns.md).

## Определи context contract на один model call

Зафиксируй как минимум:

```yaml
identity: user / agent / tenant
scope: project / task / phase
purpose: решение, которое модель принимает сейчас
allowed_sources: источники и режим read/write
freshness: требования к актуальности
token_budget: лимиты входа, выхода и резерв на инструменты
provenance: как фрагменты связываются с источниками
write_back: что, куда и при каком условии разрешено сохранять
```

Context contract должен передаваться через весь маршрут. ACL только на уровне базы недостаточен, если tenant/project теряются между worker, gateway, retrieval и cache.

## Спроектируй runtime-сборку

1. Нормализуй запрос и сформируй task envelope.
2. Выбери минимальный набор инструкций, навыков и инструментов.
3. Реши, что загрузить сразу, а что получать just-in-time. Предпочитай progressive disclosure: сначала индексы, метаданные и ссылки, полный материал — по необходимости.
4. Выполни hybrid retrieval, когда это оправдано: lexical/FTS + semantic + metadata/graph/time filters.
5. Проверь ACL, freshness и provenance до включения фрагмента.
6. Rerank, deduplicate и разнообразь доказательства; не заполняй окно похожими чанками.
7. Собери context pack в явном порядке приоритетов и оставь резерв для ответа и следующих tool calls.
8. После шага сохрани только разрешённое: рабочее состояние, устойчивую память или проверяемый артефакт.

Не вводи сложный memory/RAG-компонент только потому, что он существует. Начинай с простейшего механизма, который проходит evals.

## Управляй длинными задачами

- Используй trimming для локальных задач, где старые ходы не нужны.
- Используй compaction на смысловых границах работы, сохраняя цель, решения, ограничения, открытые вопросы, ссылки и незавершённые действия.
- Держи структурированные рабочие заметки вне окна контекста.
- Изолируй глубокое исследование в отдельном контексте или исполнителе и возвращай компактный результат с доказательствами.
- Не принимай summary за источник истины: решения и факты должны ссылаться на артефакты или первичные данные.

## Память и write-back

- Разделяй session history, working state, episodic memory, semantic/project memory и human-reviewed artifacts.
- Записывай память только после проверки полезности, области действия, срока жизни, происхождения и риска prompt injection.
- Конфликтующие факты не перезаписывай молча: сохраняй время действия и provenance либо запрашивай разрешение.
- Общую справочную память по умолчанию делай read-only; пользовательскую и проектную память изолируй идентификаторами владельца и проекта.

## Проверяй результат, а не наличие компонентов

Измеряй отдельно retrieval и поведение агента. Минимальный набор:

- recall/precision или hit rate нужных доказательств;
- grounded correctness и корректность цитат;
- сохранение цели и решений после compaction;
- утечки между пользователями и проектами;
- доля полезных токенов, input/output tokens, latency и стоимость;
- успешность выбора инструментов и завершения задачи;
- качество memory write и последующего recall.

Для аудита и тест-плана прочитай [references/audit-and-evals.md](references/audit-and-evals.md).

## Выбирай реализации осознанно

При выборе библиотек сопоставляй требуемый механизм, зрелость, способ развёртывания, модель доступа, наблюдаемость и стоимость. Не выдавай GitHub stars или заявления автора за доказательство качества. Для актуального обзора первоисточников и open-source реализаций прочитай [references/ecosystem.md](references/ecosystem.md) и при существенном выборе перепроверь текущие версии в интернете.

## Формат результата

Дай пользователю:

1. короткий вывод: что уже есть и чего не хватает;
2. карту текущего потока с уровнем подтверждения;
3. целевой поток context assembly;
4. таблицу разрывов `проблема → риск → изменение → проверка`;
5. поэтапное внедрение от минимального рабочего контура;
6. evals и наблюдаемые критерии приёмки.

Отвечай на языке пользователя. В схемах визуально отделяй текущую и целевую архитектуры.
