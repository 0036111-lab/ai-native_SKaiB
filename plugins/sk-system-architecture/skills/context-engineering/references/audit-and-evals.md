# Audit and evals

Читайте этот файл при проверке существующей системы, диагностике или подготовке критериев приёмки.

## Evidence table

Для каждого компонента фиксируйте:

| Поле | Смысл |
|---|---|
| Runtime | где процесс реально выполняется |
| Configuration | что настроено и включено |
| Input contract | какие identity/scope/purpose/budget получает |
| Read path | какие данные способен получить |
| Write path | что и куда способен изменить |
| Isolation | как разделены user/tenant/project |
| Evidence | config, code, API response, log, live probe |
| Checked at | время наблюдения для меняющегося состояния |
| Status | confirmed / configured-unverified / unknown / proposed |

`Checked at` нужен не для украшения схемы, а чтобы отличать текущее состояние от устаревшего наблюдения. В обзорной схеме его можно вынести в реестр доказательств.

## Failure taxonomy

Диагностируйте по этапам:

1. **Intent:** неверно понята задача или scope.
2. **Selection:** не выбраны нужные skills/tools/sources.
3. **Access:** ACL отклонил запрос либо пропустил лишнее.
4. **Retrieval:** нужный материал не попал в candidates.
5. **Ranking:** нужный материал найден, но оказался ниже cut-off.
6. **Assembly:** фрагмент потерян при dedup/compression/budgeting.
7. **Attention:** материал был в prompt, но модель его не использовала.
8. **Action:** модель выбрала неверный tool или неверные параметры.
9. **Write-back:** полезное состояние не сохранено, сохранено не туда или отравило память.

Не пытайтесь исправлять все классы проблем увеличением top-k или размера окна.

## Eval suites

### Retrieval

- golden queries с ожидаемыми sources/facts;
- recall@k, precision@k, MRR/nDCG при необходимости;
- проверка metadata, temporal и ACL filters;
- контрастные запросы между похожими проектами;
- запросы с отсутствующим ответом.

### Assembly

- соблюдение token budget;
- сохранение обязательных инструкций;
- отсутствие дублирующих chunks;
- provenance для каждого утверждения;
- стабильность при изменении порядка candidates;
- compaction continuity.

### Agent outcome

- task success и корректность результата;
- groundedness и citation correctness;
- правильный выбор и число tool calls;
- отсутствие запрещённых действий;
- latency, input/output tokens, cache hit и стоимость.

### Memory

- precision полезных записей;
- recall в последующих задачах;
- корректный user/project scope;
- обработка устаревших и конфликтующих фактов;
- устойчивость к prompt injection и data poisoning;
- возможность просмотра, исправления и удаления памяти.

## Minimum acceptance tests for a shared gateway

1. Два проекта с похожими терминами не получают данные друг друга.
2. Worker без права на источник не видит ни content, ни cache result.
3. Нужный факт находится как по точному термину, так и по семантическому перефразированию.
4. Более свежий факт выигрывает у устаревшего, но старый остаётся доступен для исторического запроса.
5. После compaction сохраняются цель, принятые решения и незавершённые действия.
6. Полный документ открывается только при необходимости; обычный запрос получает компактные фрагменты.
7. Большой tool output не переносится дословно в следующие шаги.
8. Memory write нельзя выполнить из недоверенного содержимого без установленной политики.

## Reporting

Не смешивайте в одном цвете наличие компонента и успешность end-to-end маршрута. Лучше показывать отдельно deployment state, configuration state, observed read/write capability, последнюю проверку в реестре доказательств и target-only элементы отдельным контуром.
